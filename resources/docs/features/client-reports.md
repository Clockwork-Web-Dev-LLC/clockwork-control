Client reports are the monthly "here's what we did for your site" email. Everything lives in the `client_reports` module (`modules/ClientReports/`), and the sidebar entry is **Client reports** (`/client-reports`). Turn the module on or off from the Module Directory like any other module. When it's off, the routes and nav item go away.

Open issues, decisions and next steps are tracked separately in [Internal → Client reports tracker](/docs/internal/client-reports-tracker).

## The three tabs

**Reports** (`/client-reports`) holds the history table and the manual **Generate** form. Pick a site, a template, a date range, and optionally a client name, email and a custom note. You land on a preview page with a **Print / Download PDF** button. A period is always whole days: the compiler runs from the start of the first day to the end of the last, and `meta.period_days` is a whole number (31 for October).

The preview's **Email version** button (`/client-reports/{report}/email`) shows the email exactly as the client gets it, with the To and Subject lines, any review reasons, and the plain-text version that text-only mail apps show. The preview page lays sections out differently (updates as a table, for one), so check the email version before sending.

The preview, the HTML email and the plain-text email show the **same sections**: one rule, `Modules\ClientReports\Support\ReportSections::visibility()`, decides from the stored report which sections the client sees, and all three views use it. A section that was compiled but has nothing true to show (no hours logged, no form tests, backups not verified, the probe doesn't check the site, no speed test, traffic missing or not believable) is left out of all three. On the operator preview it shows instead as a grey, dashed note that doesn't print, saying why, e.g. "Work log hidden from the client: no hours were logged this period." The preview's updates table and its counts come from the same cleaned-up rows as the email (`ClientReportMail::updateRows()`: WordPress core, themes and plugins), and it has a Contact forms section with the email's wording.

The preview page is also what prints as the PDF and what the public `/reports/view/{token}` route serves. So operator-only things (the hidden-section notes and their badges, review reasons, the backup check or relay error, "no blocker reports to Control", the core-files "no checksum path" note, 429 blocked time, traffic coverage, the Recompile button and action messages, who logged each work-log entry) appear only on the operator preview, never print, and never appear on the public page.

An unsent scheduled report has a **Recompile** button (↻ in the history table, and on the operator preview). It compiles the same period again from current data and never sends anything; see [Refreshing held drafts](#refreshing-held-drafts-recompile).

The paper-plane button in the history table emails a report to every address in its `client_email`, which scheduled reports fill with all their recipients, comma-separated. On a **Partly sent** report it only emails the addresses that don't have it yet; on a **Sent** one it sends to everyone again. If a report has no address saved, the button asks for one (you can enter several, comma-separated) and saves it on the report. A **superseded** report can't be sent. Sending a scheduled report by hand stamps its schedule's `last_sent_at`, the same as an automatic send.

History statuses: **Generated** (compiled, not sent), **Needs review** (held, see below), **Outdated: recompile** (unsent and compiled under older report rules; it can't be sent until it's recompiled), **Partly sent** (some recipients got it), **Sent**, and **Superseded** (a newer report for the same schedule and period replaced it before it reached anyone, after a recompile or a scheduled rerun).

**Templates** (`/client-reports/templates`) control which sections go into a report. A template is just a name plus a list of section keys. Exactly one template is the default. You can't delete the default or the last remaining template, and un-ticking "default" on the only default is silently ignored.

**Scheduling** (`/client-reports/schedules`) allows one schedule per site, enforced by a unique index on `site_id`. Each schedule has a frequency (`weekly` / `monthly`), a recipients list, a template, and a delivery mode:

- **`auto`** compiles and emails every recipient, unless something needs a person first, in which case it's held as a draft (see **Hold for review**). A schedule's **first** report is always held. It needs at least one recipient.
- **`draft`** only compiles, so someone can review the report before sending it by hand. Drafts are flagged with the same review reasons.

Schedules only send for **care-plan sites** (see below); the list marks the others **No care plan — won't send**.

Each row also has **Pause/Enable** and **Send now** buttons. **Send now** runs the schedule for **last month**, exactly like the 06:00 run, so on a schedule that has sent before it emails a clean report straight away. To refresh a held report, use **Recompile** on the report instead.

## A report is a snapshot

This is the key thing to understand. `ClientReportCompiler::compile()` queries the monitoring tables once and writes everything into `client_reports.sections_data` as JSON. That includes the branding (colours, logo, company name), captured at generation time. The preview page and the email both render from that JSON and never from live data.

So if you change the branding or fix a data bug, existing reports won't change. Recompile an unsent scheduled report (see [Refreshing held drafts](#refreshing-held-drafts-recompile)), or generate a new one.

## Where each section's numbers come from

The rule for every section: **if we didn't check it during the period, the report says so** ("Not checked this month") or leaves it out. It never shows a passing default, because the email goes to clients as-is.

| Key | Source | Period | When there's no data |
|---|---|---|---|
| `updates` | `action_logs` rows in `ActionLog::UPDATE_TYPES` with `ok = true`, minus runs that changed nothing. What was still **waiting at the period end**: plugins, themes and WordPress core from the Companion snapshot (`pending_plugins`, `pending_themes`, `pending_core`), plus any plugin/theme/core update applied **after** the period (`updated_since_period`, for a held report recompiled days later, or a manual update). The 06:00 UTC run comes before that night's snapshot refresh (01:30 ET) and nightly updates, so "at the period end" normally means the previous day's snapshot, about 17h before the end. A snapshot taken more than 48h before the period end (Companion stopped answering) can't say, so all three are unknown (`snapshot_stale`) and the report is held. | In period | "Everything was already up to date" only when we know nothing was waiting (`ClientReportCompiler::updatesWereWaiting()`, shared by both emails and the preview); otherwise "No updates were applied this month" |
| `uptime` | `site_uptime_events`: each `down` runs until the next event of another kind, clamped to the period (an outage already open at the start counts from the start). The period here is its calendar days **in the report timezone** (below), the zone outage times are shown in, so an outage at 01:00 UTC on the 1st belongs to the month before, where it reads "Sep 30, 9:00 PM EDT". The other sections list whole UTC days, as their sources record them. SLA-exempt outages are skipped. **Uptime monitoring that began part-way through the period** is measured from when it began: the first successful probe's seed transition in `action_logs`, or the site's `created_at` when that falls inside the period (a backfilled seed doesn't count). Starting on the period's first day (local) counts as the whole period. The uptime row and preview tile then say "(monitoring began Oct 17)", and the report is held with "Uptime monitoring began Oct 17, so uptime covers only part of the month." "Monitored" means the probe really checks the site: monitoring on, the same server/ignore-list rules as `clockwork:check-site-uptime`, and checked within a day of the period end (`uptime_last_checked_at`). When it should be monitored but hasn't been checked lately (`probe_stopped`), the report is held. |

| `security` threats blocked | `blocked_ips` rows banned in the period (lockouts pulled from Gatekeeper or Limit Login Attempts Reloaded) | In period | A number only when it was **measured**: bans in the period, or a WordPress site with an active blocker (Gatekeeper capability or LLAR) on a non-ignored server whose fail2ban jail is provisioned and whose lockouts were pulled in the period's last day or after (a pull that stopped mid-month can't vouch for the rest). Review-queue rows are not evidence: they are the lockouts that **didn't** become bans. When any lockout created in the period is still `pending`/`queued_for_ban` or `failed` (`unbanned_lockouts`), the count is hidden even beside real bans. This doesn't hold the report (with the count hidden the email is accurate); the operator preview says "Not measured (N lockouts this period never became a ban)". Otherwise `blocked_threats_count` is null and the tile and row are left out, so an unmeasured 0 never reads as "no attacks". "Block attackers at the server" appears only where that jail exists (`blocks_at_server`); elsewhere the copy says "block malicious visitors". |

The operator preview says why, and for a shown section how many days were recorded and from which source. "Data transferred" is left out when the host reports no byte counts (Pressable). Reports compiled before traffic had a status show as they always did. |

The email lists the **last 10 days of the period**, one row per day, plus how many days that month had a backup. That count is left out when our records for the site start after the period's first day (`covers_period` false): Pressable keeps only ~8 days, so the month we started recording would otherwise read as "backed up on 9 days". Every compiled report carries `meta.schema_version` (currently **6**: 2 = honesty fixes, 3 = recorded backups list, 4 = whole-number period lengths and the support URL fix below, 5 = partial malware scans, the core-file and threats-blocked rules and slug-joined vulnerability holds, 6 = uptime measured over the period's days in the report timezone, the coverage start split from the uptime monitoring start, and SSH scans complete only when every check proved it finished). Keys added since (coverage start, 429 blocked time, traffic status, backup `suspect`/`failing`, `malware_truncated_checks`) are read with defaults, so older reports render as they always did. `meta.period_days` is the period's length in whole days (31 for October). Reports compiled before the honesty fixes have no version. The views treat their vulnerability line as "Not checked" and hide their forms numbers, because those were computed wrongly.

### Backup recording

`clockwork:record-site-backups` (core, `App\Services\Backups\SiteBackupRecorder`) reads every active site's backups from its source and upserts them into `site_backups`, keyed by source and the source's own id. It also writes one `site_backup_checks` row per site saying whether the read worked. Rows are **kept after the source prunes them**, so re-generating an old report still has the evidence. A failed read never deletes or zeroes anything; it only marks the check as failed, logs `site_backups.record_failed`, and makes the run exit as failed so it shows red in Scheduled Jobs. It's all reads: Pressable's backup endpoints are allowed in view-only mode.

Pressable's database backups are hourly, so one row per UTC day is kept, keyed `day:YYYY-MM-DD`; a later run's newer pick replaces it. A SpinupWP run is labelled by what's actually in the bucket (files, database, or both), and a run first seen mid-upload is replaced once the rest lands. Empty (0-byte) objects don't count as backups.

Section keys and labels are defined once in `ClientReportTemplate::SECTIONS`. Adding a section means adding it there, adding a `compileX()` method in the compiler, adding its show/hide rule (and hidden note) to `ReportSections`, and adding a block to the preview and both email parts. Wording shared by the three views (outage times, backup destination, vulnerabilities) lives in `Modules\ClientReports\Support\ReportPhrases`.

## Scheduled sending

`clockwork:send-client-reports` is registered by the module itself (`ClientReportsServiceProvider::scheduledTasks()`), not in `routes/console.php`. It runs daily at **06:00 app time** (UTC on our install). On each run:

1. It skips paused schedules, inactive sites, and schedules whose `next_run_at` is still in the future. It also skips sites **without a care plan**: reports are a care-plan service, and those sites get no nightly updates or security scans, so their report would be empty or wrong. The schedule still moves on to next month, so turning the care plan back on never sends a report for a month the site didn't have one. The Schedules list marks these **No care plan — won't send**, and **Send now** refuses them. Each run writes **one** `action_logs` entry (`client_report_skipped`, actor `scheduled`) listing the domains it skipped for having no care plan, with `details.reason = no_care_plan`, since a scheduled run's console output isn't kept.
2. It skips `auto` schedules that have no recipients.
3. It compiles **last calendar month** using the schedule's template, and saves the report with `schedule_id` set. For `auto`, if a report from this schedule already exists for the same period and isn't held, it **reuses that one** instead (see below), including one that's already been **sent** (for example finished by hand after a failed run), so nobody is emailed twice; a held one is recompiled.
4. **Hold for review.** Any report that hasn't reached anyone yet is checked by `ReportReviewFlags`. If anything needs a person first, an `auto` schedule keeps it as a draft instead of emailing it, the reasons are saved in `meta.review_reasons`, and the schedule moves on to next month. The history table shows **Needs review**, and the preview lists the reasons. Send it by hand from the history table once it's checked, or press **Recompile** first to refresh it (see [Refreshing held drafts](#refreshing-held-drafts-recompile)). Held reports are never sent automatically: running the schedule again (**Send now**, `--force`) in the same month recompiles last month from current data and checks again, and the older copy is marked **superseded** so it can't be sent by mistake. Draft-mode reports get the same check, so the first-run drafts show **Needs review** too, and any report that hasn't reached anyone is checked again before an auto send. The reasons show only in our preview, never on the public view. The rules (one reason each, worded for the reviewer):
   - **Coverage:** the site was added after the period's first day ("Monitoring began Oct 19, so this report covers only part of the month."); separately, uptime monitoring began later than that ("Uptime monitoring began Oct 17, so uptime covers only part of the month."), or only after the period, when the Uptime section is left out. Dates are read in the report timezone.
   - **Malware:** the latest scan came back `warning` or `issues_found` (the reason names the finding kinds and the scan id, e.g. "php_in_uploads ×4 (scan #123)", and says when the scan also stopped early); the latest clean scan was partial ("Partial scan": stopped at a limit, an SSH check hit its result cap, or an SSH scan from before cut-short scans were tracked); or an earlier scan in the period found malware that the latest one didn't.
   - **Core files and blocklists:** core files differ from the release; no core-file check ran although the host supports one; the site is on a blocklist.
   - **Vulnerable plugins:** joined by the plugin's file slug, a plugin with a known vulnerability whose update waiting at the end of the month reaches the fixed version but wasn't applied, or whose updates are paused (auto-paused after failures, or by hand). A vulnerability on its own doesn't hold a report (about a third of sites have one at any time).
   - **Backups:** none found, stopped before the last 10 days, couldn't be checked, `suspect` (database backups far smaller than the database), `failing` (our relay has been failing, with its error), a daily source that missed more than 3 days of a fully covered month, or our relay's first archive coming 2 or more days after the period start (or after the site joined, if later) on a relay site: the S3 listing is the whole history, so its oldest archive is when archiving began, not where records start ("Off-site backups began on Oct 29, 2026; none were made before that this month …", kept as `archives_began`).
   - **Traffic:** `partial`, `suspect` or `no_data` (the section is left out and the reason says why).
   - **Contact forms:** lab checks not all accepted ("the forms accepted 18 of 19 automated check submissions"), or live tests where the site didn't report the email as sent.
   - **Uptime:** the probe hasn't checked the site lately; the site was still down at the end of the month; the monitor was blocked (HTTP 429) at the end of the month, which is said instead of "still down".
   - **Updates:** Companion hasn't reported in the 48h before the period end, so waiting updates and vulnerabilities are out of date; or no plugin, theme or core update was applied all month although some were known to be waiting (named in the snapshot, up to five, or applied after the period), so the client would read "No updates were applied this month" while they were failing or paused.
   - **First report:** it's the schedule's first (`last_sent_at` is empty), so a new client's first email is always seen by a person. Send it by hand; after that, clean reports send themselves. This applies to `auto` schedules only, since a `draft` schedule's reports wait for a person anyway.
5. For `auto` schedules, it sends one email per recipient who isn't already in the report's `sent_to`. Once everyone has it, it marks the report `sent` and stamps `last_sent_at`.
6. It moves `next_run_at` forward: the 1st of next month for monthly schedules, or now plus 7 days at midnight for weekly ones. The midnight snap is on purpose, so the next 06:00 run sees it as due. Before this, runs used to slip a day every cycle. If any recipient failed, `next_run_at` **doesn't** move, so tomorrow's run retries.
7. If a site's report **crashed** (an exception while compiling or saving it), or any recipient's email **failed** (a mail outage, say), that site stays due and is retried tomorrow, the other sites carry on, and the command exits as **failed**, so the Scheduled Jobs row turns red. Crashes are in `laravel.log` as "Failed sending scheduled client report for …", failed recipients as "Client report #… failed to send to …". Scheduled Jobs only stores the status and duration, not the per-site lines; to see those, run the command by hand: sites already handled print "skipped (not due until …)", anything still due runs again.

The command and the **Send now** button share the same code: `ScheduledReportRunner`, with delivery in `ClientReportSender`. The **Recompile** action uses the same runner (`ScheduledReportRunner::recompile()`) but never reaches the sender.

**Recipient imports.** `clockwork:import-report-recipients <csv>` (dry run unless `--apply`) adds recipients to existing schedules and creates missing ones as monthly `auto` schedules. A CSV row is no proof the client pays for reports, so a schedule it creates for a site **without an active care plan** is created **disabled** (the dry run says "no care plan: created disabled"), unless `--include-no-care-plan` is passed. Schedules created by earlier imports are left as they are.

### When a send fails part-way

Every successful delivery is written to `client_reports.sent_to` straight away, before the next recipient is tried. If one address fails, the report stays `generated` (shown as **Partly sent** in the history table), the failure is logged, and the schedule stays due. The next run picks up the **same report** and only emails the addresses that are still missing. Clients who already got it never get a second copy, and you don't end up with a pile of duplicate reports while a mail outage lasts.

Manual runs:

```bash
php artisan clockwork:send-client-reports                   # only what's due
php artisan clockwork:send-client-reports --force           # ignore next_run_at
php artisan clockwork:send-client-reports --site=example.com  # one site (id or domain)
```

Careful: `--force` and **Send now** send for real on an `auto` schedule. A held report isn't emailed only because its fresh copy is checked again, and a schedule that has never sent always holds its report as the first; once a schedule has sent (`last_sent_at` set), a clean fresh copy goes out straight away. They also always compile **last month**, so from the 1st they no longer reach the previous month's drafts. To refresh a draft, use **Recompile**. On a dev copy, check `MAIL_MAILER=log` first.

## Refreshing held drafts (Recompile)

**Recompile** (`POST /client-reports/{report}/recompile`, route `client-reports.recompile`) refreshes an unsent scheduled report from current data. It's the safe way to pick up whatever changed since the report was compiled: hours logged, a scan rerun, a backup recorded, a fix in Control itself after a deploy.

- **Who gets the button:** scheduled reports that haven't reached anyone, i.e. status `generated` with an empty `sent_to` (`ClientReport::canRecompile()`). It's on the history table (↻) and the operator preview, never on the public view. Sent, partly sent, superseded and hand-generated reports are refused with a reason.
- **What it does:** `ScheduledReportRunner::recompile()` compiles the report's **own** `period_start`–`period_end` (not "last month"), with the schedule's current template and recipients, keeps any custom note, marks the old copy **superseded**, and runs the same review check as a scheduled run. An `auto` schedule that has never sent holds the new copy as its first report; a `draft` schedule doesn't add that reason. It runs in a transaction, so if compiling fails the old copy stays live.
- **What it never does:** send email, stamp `last_sent_at`, or move `next_run_at`. A recompiled copy with nothing to review still waits for someone to send it from the history table.
- **Outdated reports can't be sent as they are.** A report whose `meta.schema_version` is below `ClientReportCompiler::SCHEMA_VERSION` was compiled under older rules (`ClientReport::isStale()`). While nobody has it, the history table shows **Outdated: recompile** with no paper-plane, the operator preview says so, and `send()` refuses it ("Press Recompile …", or "Generate a new report …" for a hand-made one) without stamping `last_sent_at`. A scheduled run doesn't reuse such a copy either: it recompiles. A **Partly sent** or **Sent** report can still finish delivering or be resent, since its recipients already have that copy.

To refresh the drafts after a deploy:

1. Deploy and run the migrations, so the new data the compiler reads exists.
2. Run `php artisan clockwork:recompile-held-client-reports` (add `--dry-run` first to list them, `--outdated` for only those compiled under older rules, `--site=` for one site). It recompiles every unsent scheduled report the same way the button does and prints each new copy's review reasons; it never sends. Or open each held report (history → **Needs review** / **Outdated**) and press **Recompile**. You land on the new copy, with a message saying it was recompiled for its period and that nothing was sent, plus any reasons it's held for.
3. Check the new copy's review box and its **Email version**. Fix what you can and recompile again; send it by hand from the history table only once it's right.

Don't use **Send now** or `clockwork:send-client-reports --force` to refresh drafts: they compile last month only, and on a schedule that has sent before they email a clean report immediately.

## The email

`ClientReportMail` puts the whole report in the email body: an HTML view plus a plain-text one (`emails/report*.blade.php`). The logo is embedded inline via `BrandLogo` so it still shows when remote images are blocked. Update rows are cleaned up into client-friendly lines ("TranslatePress 3.3.6 → 3.3.7"). The From line is the configured sending address (`MAIL_FROM_ADDRESS`) under the report brand's company name, so the inbox shows the agency whatever `MAIL_FROM_NAME` says; the **Email version** page shows it. Reply-To is the report brand's support email. The footer text, when set, appears in both the HTML and plain-text parts.

There's deliberately **no "view online" link**: Control lives on a private network clients can't reach. That's also why the public `/reports/view/{token}` route exists but isn't linked anywhere useful.

## Branding

Colours, logo, company name and support details come from **Settings → Companion & White Label → Client Reports** (`/settings/companion?tab=reports`, stored as `reports.branding.*`). Blank fields fall back to the shared Companion identity. The support URL falls back from the reports value to the shared Companion support URL, then to the Agency Website; it never falls back to Control's own URL (`APP_URL`), which is private. The settings form only accepts public http(s) addresses there, not localhost or private-network hosts. The email doesn't link to it today; it's stored with each report. See [Companion & White Label](/docs/features/companion-branding).

The **primary colour** fills the header banner of both the email and the operator preview (and the section underlines); the logo sits on it, so use a logo that reads on that colour. The preview keeps the colours when printed or saved as a PDF. Because branding is captured in the snapshot, regenerate a report to see a colour change.
